# 近期功能实现文档

近期功能实现文档是仓库内的结构化文档，用来解决代码更新快、人人记忆跟不上的问题。每个业务域对应一个 `.governance/logic/<domain>.json` 文件，随 git 入库，全团队共用同一份。每个条目都带指向代码的指针，指针由 `file`、`symbol`、`line`、`end`、`role` 组成；条目按 `group` 与 `kind` 树状划分。

`govern logic` 子命令、`.governance/logic/` 目录、`.governance/logic/*.json` 文件、`LOGIC-BROKEN` / `LOGIC-STALE` 规则名以及插件 tab 标识 `logic` 均为机器标识，保持不变；人读名称统一为「近期功能实现」。

## 条目字段

| 字段 | 内容 |
| --- | --- |
| `id` | 条目标识 |
| `title` | 条目标题 |
| `group` | 斜杠分组路径，默认 `""`；空值挂在域根 |
| `kind` | 分类：`module` 功能模块 / `service` 服务与进程 / `resource` 服务器资源 / `api` 接口契约 / `data` 数据与存储 / `task` 任务与调度 |
| `summary` | 逻辑摘要 |
| `narrative` | 为什么这样写、业务流程与取舍 |
| `flow` | 流程描述 |
| `sections` | 条目细节小节，元素包含 `title`、`body`；至少 3 个小节 |
| `pointers` | 指向代码的指针，包含 `file`、`symbol`、`line`、`end`、`role`；每条目 2–5 个 |
| `source_hash` | 源码内容哈希，只含内容、不含行号 |
| `ack_hash` | 复核盖戳的当前内容哈希 |
| `entry_status` | 条目状态，由引擎按当前代码现算，取 `fresh` / `stale` / `broken` / `draft` |

## 域字段

| 字段 | 内容 |
| --- | --- |
| `overview` | 域级概述：系统边界与组件总览、数据流向、进程/模块分工，5–8 句 |
| `crosscut` | 域级横切小节，元素包含 `title`、`body`；覆盖并发与锁、超时与预算、开关清单、降级链、观测与门控 |

## 两层维护

机械层包括指针行号与 `source_hash`，由 `govern logic sync` 自动刷新：`sync` 重定位指针行号并回写 `source_hash`，报告 `moved`（内容未变，仅行号移动）、`changed`（内容变了）、`broken`（指针失效）、`unchanged`。

叙事层包括 `summary`、`narrative`、`flow`、条目 `sections`、域级 `overview` 与 `crosscut`，由 AI 或人编写与维护，`sync` 绝不动它。

## 状态

状态按实时源码内容判定：引擎用当前代码现算 `entry_status`，并与 `ack_hash` 比较；`source_hash` 只含源码内容、不含行号。因此不跑 `govern logic sync`，`scan` 与 `govern logic check` 也能检出 `LOGIC-STALE`；只移动行号、内容不变不会误报 stale。

| 状态 | 含义 |
| --- | --- |
| `fresh` | 叙事与代码同步 |
| `stale` | 代码内容改过，未复核叙事 |
| `broken` | 指针失效 |
| `draft` | 新起草，未复核 |

## 树状划分

- 条目用 `group` 与 `kind` 归位：`group` 是以斜杠分隔的分组路径，默认 `""`；`kind` 取 `module`（功能模块）、`service`（服务与进程）、`resource`（服务器资源）、`api`（接口契约）、`data`（数据与存储）、`task`（任务与调度）。
- `group` 第一层固定用中文分类名：功能模块、服务与进程、服务器资源、接口契约、数据与存储、任务与调度；第二层起按模块或资源名细分，例如 `功能模块/知识库上传`、`服务器资源/ECS 生产`、`任务与调度/索引进程`。
- 空 `group` 的条目挂在域根；一个业务域的条目超过 5 个必须分组。
- 插件按 domain → group 目录 → 条目 树状展示。

## 域组织

域分两类，阅读频率与写法不同：

- **近期功能域**：一个功能一个域（如 `kb-folder-upload` 大文件夹上传），是日常最常查的部分。条目按功能的实现模块拆分，`group` 用 `功能模块/<功能名>`；每个域配一条「配额与配置总表」条目，集中列出全部配置项、默认值、环境变量覆盖前缀与调优建议。
- **基座域**：按业务域或运行形态组织（如知识库、服务与资源），覆盖长期稳定的底层机制，平时少看但排障时必查。

新功能上线时建近期功能域；功能沉淀为稳定基座后条目可并入基座域，域文件随 git 合并。

## 内容深度

架构文档要写到「照着能定位、能复现、能排障」的深度，不是逐行复述代码。概述与细节分层：概述留在 `summary`、`narrative` 与域级 `overview`，细节一律进 `sections` 与域级 `crosscut`。

### 条目 `sections`

- 至少 3 个小节。近期功能域的条目优先用「功能逻辑 / 配置与限额 / 边界与异常 / 使用与验证」菜单：功能逻辑写状态机、阶段与分支；配置与限额逐项列配置名、默认值与覆盖方式；边界与异常写上限、拒绝条件与恢复路径；使用与验证写怎么触发、怎么单测。基座域条目从「处理流程 / 核心机制 / 数据与契约 / 并发与事务 / 配置与限额 / 失败与降级 / 观测与测试 / 部署与资源」中按实际形态选取。两套菜单都不适用的小节不写。
- 每个小节的 `body` 至少 3 句，且必须写可核查细节：机制名、关键分支条件、配置项与默认值、数据结构/表名/队列名、超时与重试次数、systemd 指令或端口。禁止「负责处理 XX」这类空话。
- 小节只写当前实现的事实与取舍，不写修订过程、变更历史或待办计划。

### 条目 `pointers`

- 每条目 2–5 个指针，覆盖不同角色：`入口`、`核心`、`下游`、`配置`、`测试`，按条目实际形态取用。
- 每个指针必须对应真实存在的代码位置；找不到代码对应的机制就不写指针，也不在小节里编造机制。

### 域级 `overview` 与 `crosscut`

- `overview` 写系统边界与组件总览、数据流向、进程/模块分工，5–8 句，不写细节。
- `crosscut` 按 `title`/`body` 分节写：并发与锁、超时与预算、开关清单、降级链、观测与门控。

## git 共享

`.governance/logic/<domain>.json` 随仓库入库，是全团队共用的一份事实源，不另存个人副本，也不加入 `.gitignore`。代码变更与对应条目的机械刷新、叙事复核、盖戳应在同一次提交里一起交付，避免他人拿到新代码却拿到旧解释。

合并冲突按条目 `id` 处理：合并双方叙事、核对指针后再运行 `govern logic sync` 与 `govern logic check`，不要整份选一边而覆盖另一方的条目。

## 日常命令

| 命令 | 用途 |
| --- | --- |
| `govern logic init <domain>` | 建骨架 |
| `govern logic add <domain> <id> --file F [--symbol S] [--group 路径] [--kind 分类]` | 自动定位并起草条目，可指定分组与分类 |
| `govern logic list` | 查看全部 |
| `govern logic sync [domain]` | 重定位指针行号并回写 `source_hash`，报 `moved` / `changed` / `broken` / `unchanged` |
| `govern logic accept <domain> <id>` | 复核后盖戳：把 `ack_hash` 盖成当前内容 hash，并刷新域级 `updated` |
| `govern logic check [--strict]` | 单独检查 |

例如，为 `kb-upload` 业务域建骨架：

```bash
govern logic init kb-upload
```

## AI 改代码后的标准动作

1. 运行 `govern logic sync`，重定位指针行号并回写 `source_hash`。
2. 对报告为 `changed` 的条目复核叙事与 `sections`，改好后运行 `govern logic accept <domain> <id>` 盖戳。
3. 只报告 `moved` 的条目仅发生行号移动、内容未变，无需复核。
4. 状态为 `broken` 的条目先核对并恢复有效指针；新起草的 `draft` 条目同样要复核叙事再盖戳。
5. 状态判定不依赖是否跑过 `sync`：`scan` 与 `govern logic check` 按实时源码内容现算，代码内容变了但叙事没复核就直接报 `LOGIC-STALE`。
6. 不要手工维护行号或 `source_hash`，也不要靠直接改 `ack_hash` 掩盖未复核的叙事。

## 扫描与告警

`scan` 使用以下近期功能实现文档规则，规则随 `scan`、`health` 与 `--strict` 生效，可在 `.governance/config` 的 `severity` 中覆盖默认级别。规则按实时源码内容判定，不依赖是否跑过 `govern logic sync`。

| 规则 | 触发问题 | 默认级别 |
| --- | --- | --- |
| `LOGIC-BROKEN` | 指针失效 | `error` |
| `LOGIC-STALE` | 代码内容改过，未复核叙事 | `warning` |

## OpenCode TUI 插件

插件提供第 5 个 tab「近期功能实现」，按键 `5` 切换，按 domain → group 目录 → 条目 树状展示。条目按状态着色，指针可点击跳转到代码，顶栏与侧边栏显示计数。

## 设计原理

行号天天变，机械层必须自动，不能依赖人手工维护；hash 只覆盖源码内容、不含行号，所以行号移动不会被误判成内容变化。

「为什么这样写」无法从代码推导，叙事层只能由 AI 或人维护，并通过复核提醒避免遗漏。

两个 hash 的差值把「代码动了但叙事没复核」显式暴露出来，而不是让文档悄悄失真。
